### [secscan](https://github.com/BU1lDR/security-scanner) — SCA + SAST + DAST in one Python CLI

MIT, v1.3.1.

- Every outbound request passes one authorization gate holding two separate allowlists: **Scope** (hosts you are permitted to test) and **Egress** (the tool's own data sources, such as OSV). The one raw-socket probe that bypasses HTTP — the TLS certificate check — takes that gate as a *positional* argument, so omitting it is a `TypeError` rather than a silently ungated request. `--active` without `--i-am-authorized` degrades to a passive scan instead of firing.
- That refusal is a CI gate over a real socket, not a sentence. CI starts a deliberately flawed site on loopback and runs the scanner against it as a subprocess — routes in matched pairs, one genuinely flawed and one with the guard in place, and exact set equality over which rule fired against which route, method and parameter, so a false negative and a false positive fail the same assertion. The judgement reads the server's own log of what it received rather than the scanner's exit code, because every way the rehearsal could be vacuous ends in a clean-looking `0`. The same scan then runs again with `--i-am-authorized` withheld and must put zero probe payloads on the wire. The gate exists because the tier had been verified live twice — against a flawed loopback server, then against PyGoat — and neither harness was ever committed, so both runs expired as soon as the tree moved. The PyGoat run is where the tier's POST probes turned out never to have been sent: since the first commit, `httpx` was handed a list where it wanted a mapping, the exception was swallowed by a clause written for a target that refuses a probe, and every body injection point the crawler found came back clean without a request leaving the process. The gate has since been turned on itself: a ninth mutation nobody had written — deleting one of the two guards in the open-redirect check — left it green, because no route on the site could tell that guard from its neighbour, so the site gained the route that can.
- The suite runs offline, and CI proves that rather than asking you to trust it: it runs a second time with sockets blocked and only loopback allowed. Vendor-format tokens — AWS, GitHub, Google, Slack, JWTs — are scrubbed when a `Finding` is constructed, as a backstop behind each scanner's own redaction (`AKIA****************`); the repo says in as many words that this narrows a leak rather than rules one out, because a password with no distinguishing shape looks like any other argument. SCA findings carry per-advisory fix boundaries (`Bump flask from 0.12 to 0.12.3`). Exit codes `0/1/2/3`, so a calling script can act on the result — and `3` is separate from `0` on purpose: the scan ran but a check errored, so the report is real without being a complete answer. Collapsing that into `0` would make "found nothing" and "could not look" the same output.
- A weekly workflow asks OSV whether its own declared dependency floors admit a known-vulnerable version. It found `cryptography>=42` doing exactly that — nine distinct flaws against 42.0.0, four of them HIGH, as of 19 September 2026 — so the floor moved. Nine rather than the fifteen records OSV actually returns, because GHSA and PYSEC publish the same CVE twice and a de-duplication bug was printing those nine as fifteen; the count is dated because it is OSV's to change, and the workflow re-asks rather than this line remembering. The same habit caught the scanner reporting its own SAST rule definitions as findings — nearly every hit on its own source was the rule pack matching the string literals that describe it.

### [file-integrity-checker](https://github.com/BU1lDR/file-integrity-checker) — baseline a directory, then report what changed

MIT. Stdlib-only Python CLI built from a roadmap.sh brief; `requirements.txt` is a one-line comment saying so.

- SHA-256 hashes a tree into a versioned JSON baseline, then reports modified, new and deleted files on later runs; skips symlinks, rejects path traversal in baseline entries, exits `0/1/2` for cron. `status` exits `2` when the baseline or its sidecar is *missing*, not only when the two disagree, because integrity that was not verified is not integrity that was verified fine. It printed `Baseline integrity: FAILED` and exited `0` — the function ended in an unconditional `return EXIT_SUCCESS` — and survived because `show_status` appeared in none of the tests and CI only ever called it straight after `init`, on a healthy tree, under `set -e`, where a correct `0` and an unconditional `0` are the same green tick. The fix landed together with in-process tests and a CI step that appends one byte to the baseline and asserts `2`.
- Much of the suite feeds it hostile input and asserts that it refuses to run rather than trusting the file it was handed — absolute POSIX, Windows, UNC and drive-relative paths, `..` traversal, MD5 declared as the algorithm, wrong-length and non-hex digests, an unsupported schema version. The baseline carries a `.sha256` sidecar so tampering is detected, and the README calls that digest unkeyed rather than implying it stops an attacker.
- CI tests two of the badges at the top of that README — `Python 3.8+` and `Linux | macOS | Windows` — rather than just displaying them: Python 3.8 through 3.14, each in its own official Docker image on Linux, plus Linux, macOS and Windows at 3.12 and 3.14, with nothing installed in any job, because an empty environment is the only thing that actually tests standard-library-only. One step fails the build if discovery collects no tests, since on Python 3.11 and earlier `unittest discover` exits `0` when it finds nothing, and 3.8 through 3.11 are in the matrix. A third job holds the test count quoted in the README and in the repository's GitHub description — the one copy no commit can reach — to what discovery actually collects, reading every quoted figure rather than the first. The matrix earned itself within a day: a test-file cleanup that is clean on every interpreter installed on the development machine raises `KeyError` on 3.8 and 3.9, and the container matrix at the floor the badge claims is what found it.

### [Retail customer segmentation](https://github.com/BU1lDR/retail-customer-segmentation) — 1,067,371 transaction lines

UCI Online Retail II (CC BY 4.0), deliberately not committed.

- Nine individually logged cleaning steps take 1,067,371 raw lines down to £20.5M of reportable revenue, of which £17.5M — 85.4% — carries a customer ID and is therefore all the segmentation can actually use.
- Names the 683 high-value accounts worth £1,689,620 that have stopped ordering. The top 20% of identified customers, 1,170 of them, hold 77.2% of identified revenue. RFM quintile segmentation is cross-checked against K-Means, which agrees on 80.5% of customers and is weakest on Loyal at 60.9% purity; k=4 was kept even though the silhouette score preferred k=2.
- Shows its own 12-month CLV projection running 2.91× high on a like-for-like basis, instead of quoting that projection as a result, and states what the data cannot support: 22.9% of cleaned lines carry no customer ID at all. Every computed figure above is a named key in a committed `outputs/facts.json` (the nine cleaning steps are rows of its `clean_log` table), and CI holds the README, the notebook's prose, the notebook's committed cell outputs and the `.docx` to it — the README by distinctive rendered numbers, with the five it cannot tell from a coincidental match named in the check rather than quietly skipped, k=4 and k=2 among them; the other three by anchored figures, each found by the sentence around it rather than by matching a number anywhere in the file, and an anchor that fits two different figures is a failure rather than a first-match, because these documents quote their own past mistakes on purpose. The stale figure the check cites as its reason to exist — 20 off-peak cohorts in the notebook's prose where `facts.json` says 18 — was first credited to the notebook-against-its-builder comparison, which cannot catch it: a figure typed wrong in the builder is wrong identically in both files. That correction stays in the README rather than being edited out, and the rewrite that extended the check to the committed artefacts also found one of its own patterns had never matched anything: it wanted a literal space where the README wraps, and an `if` had been turning no match into a pass for the check's whole life.

### [Portfolio](https://github.com/BU1lDR/Portfolio) — hand-written site, no framework and no build step ([live](https://bu1ldr.github.io/Portfolio/))

HTML, CSS and JavaScript. Nothing loaded at runtime from anyone else but Google Fonts, and the deploy's CSP audit holds every host the policy admits to one of the two font origins that serve it.

- Deployed to GitHub Pages by an Actions workflow that asks the Pages API for its own base path, substitutes it into `404.html`, greps to confirm the substitution took, and fails the deploy rather than publish a 404 page that cannot find its CSS.
- `index.html` carries no `unsafe-inline` or `unsafe-eval` in any CSP directive, styles included, and the deploy asserts that across every directive rather than only checking that its inline CSS and `style-src` agree — agreement is satisfied by a page that gains a `style` attribute and gains `'unsafe-inline'` to match. `404.html` is a named exemption and keeps it for styles: a hash covers a `<style>` element and cannot cover a `style` attribute at all.
- The deterministic half of the link checker fails the deploy — local paths pointing at no file, in-page anchors matching no `id`, `target="_blank"` without `rel="noopener"`. The half that asks the other end of an external link runs weekly and notifies instead, since there is no build for a scheduled run to fail and link rot is a fact about the date rather than about the diff. Both halves exist because a repo this site linked into was deleted and stayed a 404 through two deploys and a verification pass that reported nothing, none of which had asked a link anything.
- The one figure on the résumé that goes stale without anyone editing the résumé — secscan's test count — is checked weekly against the number secscan publishes, where that repo's CI holds it to what `pytest` actually collects, so the chain from a test run to the PDF a stranger downloads has no unguarded link. It had gone stale repeatedly before that, every time secscan gained tests; the time that prompted the check, the source and the committed PDF agreed with each other and were both fifty tests behind — exactly the case the build's own source-against-PDF check cannot see. It drifted again by two a few hours later, with no diff here to review, which is the argument for the clock rather than against it. The deploy also re-derives the nine `index.html:N` references in the README's setup table from the page itself, in both directions — it caught all nine drifting inside the commit that introduced it, because a comment three lines longer had moved every block below it — and holds the command counts quoted in the README, the page and the repository's GitHub description to the one table in `js/terminal.js` that owns them; the description had said "40+ commands" over a table of fifty-one, a floor claim, which is exactly the kind no reader can see go stale.
- A wireframe torii gate drawn on a 2D canvas through a hand-rolled perspective projection, and an in-page shell with command history, tab completion, and typo suggestions from a hand-written edit distance. Exactly one of the thirty hidden commands has secrecy as the point — a command the shell will run but keeps out of `help`, tab completion and did-you-mean, because the page source is meant to be where you find it — so the completer and the suggester skip that one and not the other twenty-nine, which are hidden from `help` but findable by poking around; Tab on a two-letter prefix and a typo within two edits of it were both handing it over.
